## 1. [P1] 暂停创建与加入 Job 之间存在孤儿进程窗口

位置：[CONTRACTS.md](CONTRACTS.md) 第 67～68 行；[ACCEPTANCE.md](ACCEPTANCE.md) R03。

现有顺序：创建暂停态进程 → 加入 Job → 恢复执行 → 写入 PID/创建时间。若 Runner 在创建成功后、加入 Job 前崩溃，新进程可能既未受限、又没有持久化身份；它暂时不运行，但可能一直挂起占用资源，监控器也无法按现有记录核对它。

R03 目前只要求 Unknown 和不重复启动，没有断言这个窗口中的受管归属、进程回收或明确接管。仅增加一条 Unknown 状态不解决泄漏。

建议：优先验证 Windows 10+ 的创建时 Job 关联 `PROC_THREAD_ATTRIBUTE_JOB_LIST`，并定义控制方持有的创建阶段状态与暂停进程恢复。需要故障注入验证多 Job 失败与控制方退出，不能把创建时关联等同于所有步骤原子化。

补充验收：在 CreateProcess 返回与关联/回执的每个边界中断，证明不存在无法归属的暂停进程；既有正常运行会话仍存活。

依据：[Microsoft / Raymond Chen：创建时加入 Job](https://devblogs.microsoft.com/oldnewthing/20230209-00/?p=107812)。

## 2. [P1] Unknown 预约缺少可撤销的授权协议

位置：[CONTRACTS.md](CONTRACTS.md) 第 71、127、165 行。

现有规则正确禁止仅凭超时释放已提交预算，但没有定义如何撤销尚未执行的启动权限。若 Terminal 没有创建 Runner，系统又无法证明未来不会迟到，预约可能在本次开机期间一直占用，监控器也因“未完成提交”不能退出。反过来，手工删除记录释放预算，会让迟到 Runner 使用旧计划突破当前预算。

建议：把预约和启动权限分开；增加可持久化的撤销状态/代次，Runner 创建前必须向唯一控制方原子领取有效启动授权。撤销与领取串行竞争；已经领取或可能创建的阶段仍走核对，不能强行视为可释放。claim 文件只能防重复，不能代替预算授权。

补充验收：延迟 Runner，先撤销旧请求并启动新请求，再放行旧 Runner；旧 Runner 不创建进程，总预算不超额，确认无活动任务后监控器退出。

## 3. [P1] Git 准备阶段没有纳入资源预算

位置：[CONTRACTS.md](CONTRACTS.md) 第 65、159、217、223 行。

资源预检查发生在 worktree 准备前，但硬限额只定义给 Agent 及其后代；Git 准备进程不属于这些后代。大仓库检出、Git filters/hooks 等可能在 Agent 尚未启动时占用大量 CPU/内存/磁盘。单仓库串行只能限制数量，不能限制单次操作的资源增长；不同仓库的并发规则也没有给出整机级预算。

建议：为本应用启动的 Git 准备和相关子进程定义独立但计入总量的资源组、全局准备并发限制和磁盘余量检查。超额或中断后保留实际 Git 状态并核对；不强行删除锁或声称事务回滚。

补充验收：用临时测试仓库的受控 filter 模拟重负载，验证准备阶段同样受限、UI/桌面仍可操作，失败后目录可核对。当前机器不执行此压力实验。

## 4. [P1] 已准备工作目录缺少跨批次占用检查

位置：[CONTRACTS.md](CONTRACTS.md) 第 215～219 行；[UI-DESIGN.md](UI-DESIGN.md) “使用已准备目录”。

规格有 Git 创建锁和仓库身份，但没有“当前哪个受管 Agent 正在写哪个物理目录”的占用合同。用户第一次打开已有 worktree 后，再次选择相同目录启动第二个 Agent，会绕过独立工作目录的预期；两个本应用会话可能同时写同一文件。创建期间的 Git 锁不会覆盖后续 Agent 生命周期。

建议：按规范化物理工作目录建立受管占用记录；独立模式中的重复目录和再次使用活动目录必须阻止，或让用户明确切换为共享模式。进程状态 Unknown 时不能假定目录空闲。只能覆盖本产品已知会话，不能宣称能阻止用户在外部工具修改文件。

补充验收：跨批次、不同路径别名指向同一 worktree，第二个独立写入会话被发现；两个不同 worktree 仍可并行。

## 5. [P2] 切换 Agent 只改名字，旧程序路径和参数残留

位置：[prototype.html](prototype.html) 第 58 行。

事件处理只更新 `slot.name`，不清理或按 Agent 保存 `slot.path`、`slot.arg`。

脚本复现：先给 Pi 配置 `C:/Tools/pi.cmd` 和 `--pi-specific`，选择器改为 Codex 后，状态变为：

```json
{"id":1,"name":"Codex","enabled":true,"path":"C:/Tools/pi.cmd","arg":"--pi-specific"}
```

原型没有真的执行，因此没有发生“启动错程序”；但显示名称与实际配置已经不一致，不能把这套状态管理直接移入正式实现。

建议：配置用稳定 agentId 绑定执行器；不同 Agent 的覆盖路径/参数分开保存，切换时加载对应配置。验收要断言程序路径和 argv，不只检查显示名。

## 6. [P2] 恢复组合不会恢复目录隔离策略

位置：[prototype.html](prototype.html) 第 99～102 行；[UI-DESIGN.md](UI-DESIGN.md) U06。

保存组合只存 slots 和 layout，目录策略只存在于 DOM 文本/单选按钮。复现：在“各自独立”时保存组合 → 改为“共用原目录” → 恢复原组合，界面仍显示“共用原目录”。详细规格却要求模板包含目录策略。

建议：目录模式进入统一草稿模型和模板快照，恢复时同步控件与实际计划。模态窗口采用草稿/提交语义，取消不能让未应用的单选值在下次打开时冒充当前配置。

补充验收：跨不同目录策略保存、恢复、取消，最终计划与选择器及摘要保持一致。

## 7. [P2] “上次组合”没有快照，实际重置为第一项

位置：[prototype.html](prototype.html) 第 102 行。

`last` 没有专门恢复逻辑，落入默认分支，强制启用第 1 项。脚本复现：仅启用第 4 项 → 切到 Pi + Codex → 切回上次组合，启用项由预期 `[4]` 变为 `[1]`。

建议：明确定义“上次组合”为最近一次已应用/已启动组合或独立草稿快照，在切换前保留；如果不实现恢复，就去掉误导的选项，而非把它当“默认单开”。

补充验收：改名、改参数、只启用非第一项、改变布局后进行模板往返切换，快照字段完整恢复。
