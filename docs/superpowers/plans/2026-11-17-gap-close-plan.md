## 1. 目的

在可以判定 G4 之前，先完成四件事：

1. 让规格与代码一致：SSH 远程 Linux 主机进入正式范围，WSL 仍排除。

3. 补齐远程生命周期缺口，尤其是操作员确认释放和真实 VPS 验收。
4. 用完整门禁、远端 CI、本机长稳和人类可用性，决定能不能宣称稳定发布。

### P3 远程缺口实现

按 [远程执行规格](../specs/2026-11-17-remote-execution-spec.md) 只补合同已要求、当前缺失的行为：

1. **操作员确认释放（R28）**：核对动作必须记录操作员已查看的主机、目录、判断（进程仍在 / 已不在 / 无法判断）和释放原因；二次确认后才能把 `Disconnected` 标为终态并释放账本。无法判断时不得释放。不得提供会盲目再拉起可能仍存活的远程进程的一键重试。本阶段不做自动重连。
2. **真实 VPS 活测（R29）**：使用已有 `RemoteLiveChecks` 入口，隔离测试目录，确保运行时没有假 `ssh.exe` 遮蔽真实客户端。证据放到 `artifacts/` 下被忽略的目录；提交的文档只引用路径和结论，不写地址、用户或密钥。
3. **同步收尾证据**：`flush` 失败保留 Mutagen 会话并写入回执的路径，纳入可重复测试或已归档的定向证据。
4. **表述对齐**：代码注释和 UI 文案中的状态名与合同一致（`Settled` / `Disconnected`，不要再把断开写成简单的 `Exited`）。
5. **完整门禁**：对包含远程 UI 的工作树运行不跳过 UI/浏览器的 `scripts/test.ps1`。

远程内存上限继续明确不实现，直到另开规格。

### P4 发布门禁

- 推送后确认 GitHub `gate` 为绿。
- 按 ACCEPTANCE §11 执行本机 S0.6 长稳；CI 浸泡结果必须标明环境，不能代替本机结果。
- 安排独立人类可用性检查，覆盖窄窗口、资源不足提示、部分失败/Unknown，以及远程 `Disconnected` 核对与释放（若远程能力要对用户可见）。
- 只有 P0/P1 实现问题为零、响应性门槛通过、已知限制已写入发布说明时，才评估 G4。本计划本身不关闭 G4。

## 4. 回退

- P0 文档可以单独回退，不影响二进制行为。
- 不配置 `RemoteHosts`、槽位不填写远程主机时，产品必须保持原有纯本地行为。
- 若远程活测或 R28 实现引入回归，先回退 Wave 4，保留已提交的本地波次。
- 任何未关闭的远程缺口或脏树发布包，都不能写成稳定发布。
