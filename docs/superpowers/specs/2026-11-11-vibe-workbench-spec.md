# 面向 vibe coding 的扩展功能规格

日期：2026-11-11。状态：规划稿；未实现的能力不计入产品验收。

本规格承接用户要求：先解决启动与频繁退出，再增加实用功能；支持 Agent 参数；研究同 Agent 负载共享；参考 GitHub 项目。实施顺序见 [实施计划](../plans/2026-11-11-vibe-workbench-plan.md)。当前产品合同仍以 `docs/CONTRACTS.md` 为准，每阶段交付时再更新对应合同。

## 1. 推荐范围与顺序

目标是让用户从“开几个终端”走到“有任务、有隔离、有验证、能续接”的本机开发流程。保留 Windows 原生窗口和 Windows Terminal，避免为了增加功能先引入一套浏览器运行时。

| 顺序 | 能力 | 用户得到什么 | 通用性 |
| --- | --- | --- | --- |
| G0 | 稳定性与资源证据 | 知道为什么退出、下一次如何调整，不再只有负数退出码 | 所有受管 CLI |
| P1 | 参数预设与启动预览 | 直接选常用模型、续接等已验证参数，也可保留自定义参数 | 通用参数列表；语义按 Agent 适配 |
| P1 | 任务卡、队列与续跑 | 保存需求、验收项、分支和运行记录；资源不足时等待 | 所有 CLI；原会话续接需能力检测 |
| P2 | 批次共享资源池 | 空闲额度可被同组忙任务利用，减少固定小上限带来的分配失败 | Windows Job 支持的受管进程 |
| P2 | 改动审查与验证中心 | 看 diff、跑项目检查、对照本次提交的 CI，再决定提交 | Git 项目；CI 首先适配 GitHub |
| P3 | Omp 多会话后端 | 验证同一个运行时承载多个独立会话能否真正减少开销 | 首先仅 Omp；实验功能 |

首个扩展版本推荐只交付 P1。共享资源池先完成内核原型与故障测试，再进入产品；Omp 多会话不能作为当前崩溃的紧急补丁。

## 2. 稳定性前置门槛 G0

已观察：本机 Omp 18.18.8 的一次故障模块为 `pi_natives.win32-x64-baseline.node`，退出码为 `0xC0000409`；一个当前 Omp 作业树提交峰值约 2048.1 MiB，限制为 2048 MiB。历史两个退出作业没有保存峰值，不能据此断言两次都由内存限额导致。

隔离探针：通过 Node 加载同一原生模块，对同一输入调用 tokenizer，128 MiB Job 下触发原生分配失败并返回相同退出码，512 MiB 下通过。这验证了一个可重现机制；探针不是完整 Omp/Bun 会话的等价负载。

G0 交付要求：

1. 退出回执记录十进制与十六进制退出码、OS 提交峰值和当时 Job 上限，读取失败明确显示未知。
2. 区分“峰值接近上限”“OS 明确内存拒绝事件”“Agent 原生崩溃”，不把退出码当根因。
3. 设置说明上限包括 Agent、子 Agent、MCP、浏览器、编译器等受管子进程；规划估算与提交上限分开展示。
4. 可为未来批次调整内存参数，旧作业保持原限制；共享根 CPU 上限在活动批次存在时保持锁定。
5. 原生、集成、WPF、原型和浏览器检查通过，最终修复提交的 CI 通过。已通过的旧提交不能替代新提交。
6. 独立两任务工具负载连续 30 分钟并重复三轮，无相同异常退出；记录版本、峰值、子进程数与操作内容。没有真实负载证据时，只能标注“机制已复现、缓解已验证”，不能宣称长期稳定。

保持：不自动重放任务、不结束用户正在工作的 Agent、不热改活动 Job、不丢弃工作目录。达到硬限制仍可能分配失败，产品不能承诺有限内存下任意负载永不崩溃。

## 3. 参数预设与命令支持

### 用户流程

选 Agent → 选参数预设或逐项编辑 → 查看“程序 / 工作目录 / 每个独立参数” → 校验 → 保存或启动。沿用现有 AgentProfile.Arguments 数组，不把整个命令塞进 executable 字段。

已有能力：短参数、长参数、位置参数都可作为字符串参数传递。新增的是易用性与版本适配，不重复造一个 shell 解析器。

目标行为：

- 支持 `-x`、`--name`、`--name=value`、`--` 以及位置参数；是否被 CLI 接受由对应版本决定。
- 例如 `['--model', 'model name']` 是两个参数；参数值不额外存储 shell 引号。空字符串、中文、换行、反斜杠和分号按现有精确 argv 合同传递。
- 预设为按 Agent 隔离的命名配置；切换 Agent 不携带另一 Agent 的参数。编辑预设时复制，避免修改其他任务快照。
- 常见语义为“新会话”“续接指定会话”“模型选择”；仅对已验证版本提供按钮，不假定所有 Agent 都支持同名参数。
- 程序身份记录物理路径、版本和文件指纹；升级后旧能力缓存失效。未知参数可保留并标注未验证，不擅自删除用户参数。
- 执行前单独检查程序存在、适配器类型和参数结构。`--help`/`--version` 探测有超时、输出上限和受控进程组；不运行用户自定义 shell 片段来“自动检查”。
- 默认不展示或导出可能含密钥的原始参数；密钥通过 Agent 自身认证管理，不设计保存 token 的参数预设。

`/plan` 等是会话内命令，与启动参数不同。P1 提供复制或在终端手动输入；只有适配器提供明确协议时才增加发送按钮。不用盲目模拟键盘向未知活动窗格注入命令。

## 4. 任务卡、队列与续跑

### 任务卡

最少字段：任务名称、项目、任务说明、可勾选验收项、Agent/profile 引用、目录策略、资源需求。可选字段：基准提交、任务分支、依赖任务、优先级、用户选定的上下文文件。

每次启动冻结 TaskRevision 与执行计划，产生新的 AttemptId；编辑任务只影响下一次执行。启动器不自动阅读整仓库并发送给模型；没有 prompt 输入能力的 CLI 生成可复制的任务说明。

### 状态分离

用户工作流：草稿 → 排队 → 执行中 → 待审查 → 完成，可进入受阻或取消。

进程事实沿用现有 Pending/Creating/Started/Exited/Settled 等状态。进程 exit 0 不能直接把任务标成完成；Settled 仅证明受管进程结束。完成由用户确认，或之后明确配置的验收规则产生可审查结论。

队列规则：

- 保存草稿不启动进程；用户按“执行队列”才授权调度，授权绑定当时任务快照。
- 初期只调度完整任务，设最大运行项数；按优先级、入队顺序排序，同优先级 FIFO。
- 调度到每项时重新检查目录、依赖、CPU、物理与提交余量。等待不预先创建空闲 Agent、worktree 或长期占用启动 grant。
- 队列进入现有 monitor 串行预约路径，避免 App 关闭或多个客户端造成重复执行；队列意图与真实预约分开保存。
- 监控器重启后先恢复已有尝试，再把未启动任务置为“等待继续队列”；不默认重新执行状态未知的任务。
- “取消排队”只取消未领取项；运行项停止是独立动作，明确列出作用范围。取消队列不会杀掉已启动任务。
- 首期不承诺看透任意 CLI 内部的浏览器/编译操作。工具级重任务队列仅对经过适配器或显式包装器的调用有效，界面显示实际覆盖范围。

### 续跑

先核对原作业树已排干、工作目录物理身份、原 Agent 程序身份、会话 ID 与独占租约。适配器支持并通过版本验证时，用户明确选择续接指定会话；不支持时只“在原目录新开任务”，不伪称恢复上下文。

新 Attempt 保存 ResumeOf/TaskId/SessionRef；旧尝试和日志不覆盖。不因超时、网络错误或 App 重启自动补发最后一条 prompt。相同会话被占用或状态未知时拒绝续接，不能同时开两个写入者。

## 5. 共享负载：三种不同能力

| 能力 | 可以共享的内容 | 不能承诺的内容 | 顺序 |
| --- | --- | --- | --- |
| 共享资源额度 | 同一组内未使用的提交额度 | 不减少 CLI 重复加载；不能保证公平执行 | P2 |
| 任务/工具调度 | 控制同时运行任务数，适配器覆盖的重工具排队 | 不识别所有任意命令，不强停已分配内存的工具 | P1 整任务，P3 工具级 |
| Omp 多会话宿主 | 运行时、部分缓存及经过验证的服务 | 不共享聊天上下文/权限；进程崩溃会扩大影响 | P3 实验 |

### 共享资源池 P2

显式选择一个新批次加入池；已有作业不迁移。默认仍是独立上限模式。第一版池只在一个批次内，默认组合同一 Agent；混合 Agent 也必须由用户明确配置，不按名称暗中聚合所有会话。

候选层级：应用 CPU 根 Job → 批次内存池 Job → 单项 Job → 该项及工具子进程。挂起创建时一次性加入所有要求的 Jobs，并核验成员身份后才恢复线程。先用内核原型确认当前平台的嵌套与原子归属语义，失败时禁用池功能，不能先运行再补挂。

示例仅用于解释：池总上限 6 GiB，两个任务单项上限各 4 GiB；一个用 1 GiB 时另一个可使用到 4 GiB；两项合计不能超过 6 GiB。单项上限之和大于池上限不表示预先分配那么多内存，也不保证双方都能达到单项上限。此例不是对当前 16 GiB 主机的默认配置建议。

约束与计费：

- 池上限始终非零，单项上限始终非零且不超过池；第一版池也不超过现有可配置 8 GiB 上界及系统有效容量。
- 软预算：独立任务按各自上限相加；共享池按池上限计一次，不能再叠加每项上限。Git 准备仍独立计费。
- 硬余量：仍累计每个待运行任务的规划需求，不能因为共享就抹掉任务的基础成本；采用原有有效采样与硬保护规则。
- 运行中暂停接纳新任务并不回收已占用内存。池满仍可能使其中任意进程分配失败；通过单项上限、较小并发和任务队列降低风险，不自动扩大池。
- UI 同时展示池总量、单项限制、当前可得读数、峰值、采样时间和排队原因。峰值不能冒充当前使用量，当前读数未知不能显示零。
- 活动作业的限制只读；下个批次可修改。没有透明热迁移、breakaway 或自动跨池借额度。
- PoolId、计划摘要、策略快照加入授权绑定。取消、超时、重启恢复时，分别证明项与池的归属；未知成员继续占用并阻止新的不安全启动。
- 兼容旧 ledger：缺少 PoolId 即独立模式；旧监控器不认识池协议时必须拒绝池计划，不得静默按无池模式执行。

### Omp 同进程多会话 P3

Omp v18.18.8 SDK 文档明确说明：同一进程多个并发顶层会话各自传入独立 AgentRegistry；默认全局注册表每代只允许一个 Main 身份。因此技术上存在嵌入多会话的路径，但不是把几个现有终端附着到一个交互式 Omp 就能实现。

实验宿主要求：

- 每会话独立 AgentRegistry、SessionManager、工作目录、设置视图、事件流、请求 ID 和工具取消域；共享进程不共享提示词和自动审批。
- 不允许并发会话使用 process.chdir 等进程全局 cwd 实现工作区切换；扩展、环境变量、信号处理与全局缓存必须审计。
- 每个任务关联自己的文件 worktree。宿主 Job 只能隔离进程整体，无法给同进程某个 JS/Rust 会话建立独立内存硬限额，UI 要说明这一变化。
- 先实现两个受限会话，再测试真实扩展和工具；同宿主崩溃导致全部会话中断，保存各自事件序列与持久化位置，并停在“可人工恢复”。
- 工具级队列只拦截协议支持的 host tool 调用。非覆盖的内建工具、扩展自己创建的进程必须单独列出；不能宣称全局限流。
- MCP 复用另做兼容性表。仅支持具有多客户端会话语义且通过隔离测试的服务；不能把不同任务的 stdio 字节流直接混在一起。
- 使用现有支持的 Bun/SDK 作为可选外部依赖，按版本能力检测；基础 WPF 启动器不捆绑或自动安装运行时。
- 对照独立双 Omp 和宿主双会话：相同任务、扩展、模型、缓存预热、测量时段；目标是稳定降低合计提交内存中位数至少 20%，同时隔离测试全过。20% 是提案目标，未实测；达不到则保持实验状态，不宣传省内存。

## 6. 改动审查与验证中心

工作流：任务结束 → 变更列表 → diff → 项目检查 → 提交预览 → 用户选择提交/推送 → 对应 SHA 的 CI。

- 展示受管 worktree 与明确基准的 diff，含未跟踪文件计数；路径、二进制和大文件有界处理，不能靠读取所有文件导致再次 OOM。
- 未跟踪文件须用户选择后才纳入提交；不默认 `git add .`。提交前重新检查 HEAD、索引及选择文件的变化，防止审查和提交之间内容被 Agent 修改。
- 项目检查使用受信任的命名 CommandSpec（exe + argv + cwd）；发现 package scripts 或配置只能建议，不自动执行仓库里的任意代码。
- 每次检查保存运行 ID、commit SHA、工作区差异指纹、退出码、时长与有界日志。文件变动后旧“通过”标记为过期。
- GitHub CI 精确绑定仓库与提交 SHA；旧提交绿、新提交仍运行时显示运行中。网络不可达为未知，不转换为通过或失败。
- PR/推送等外部写入由明确的用户动作发起；不因“任务完成”自动发布。自动合并、自动删除 worktree 不在本轮范围。
- 开发服务预览先提供受管端口列表与默认浏览器打开，不先嵌入 Chromium。

## 7. 数据与模块边界

候选实体（实施前冻结具体字段，不在规划阶段直接迁移生产数据）：

| 实体 | 核心字段 | 持久化原则 |
| --- | --- | --- |
| AgentCapability | 程序指纹、版本、参数预设、会话恢复/协议能力、验证时间 | 缓存可失效；未知不等于支持 |
| TaskDefinition | Id、Revision、标题、说明、验收项、项目身份、profile 引用、依赖 | 原子保存；编辑复制 |
| TaskRun | TaskId、TaskRevision、AttemptId、ResumeOf、SessionRef、基准提交 | 尝试追加；状态由证据派生 |
| QueueIntent | TaskRevision、排序、用户执行授权、阻塞原因 | 与预约/运行状态分离 |
| ResourcePoolPlan | PoolId、BatchId、硬上限、单项策略、计划摘要 | 创建后冻结；纳入策略签名 |
| VerificationRun | TaskRunId、SHA、工作区指纹、命令 ID、结果、日志引用 | 有界日志；改动后失效 |

Core 放纯模型、策略、状态转换；Windows 放持久化、Git、进程、Job；Worker 持有队列消费、授权和运行事实；App 展示与用户操作。Omp 宿主是单独可选适配层，不能把 SDK/Bun 依赖引入 Core。

P1 优先使用独立版本文件保存任务与预设，兼容现有配置 schema 2。新增配置字段或池账本需要正式版本迁移、备份和只读未来版本保护；禁止旧程序读取新执行语义后继续执行。

## 8. 验收矩阵

| ID | 场景与必须结果 |
| --- | --- |
| VC-G01 | 相同原生模块受限分配可复现；退出证据不伪造根因；读数失败仍正常收尾 |
| VC-G02 | 活动 2 GiB 作业不变，后续 4 GiB 作业正确生效；原子归属和 CPU 保护不变 |
| VC-A01 | 参数特殊字符、空值、`--` 与短长旗标精确往返；切换 Agent 保持各自预设 |
| VC-A02 | 未验证/失效的能力缓存没有假支持；探测超时不阻塞 UI、不遗留探测进程 |
| VC-Q01 | 两客户端/重复请求/监控器重启均不重复启动；队列取消与运行任务相互独立 |
| VC-Q02 | 硬余量不足时等待，无 Agent 进程；条件恢复后只启动授权队列快照 |
| VC-R01 | 工作区或会话身份变化、租约占用、作业未知时拒绝续接；旧记录保留 |
| VC-P01 | 挂起进程已属三层 Job；共享池可借空闲额度，单项及总池限额都实际生效 |
| VC-P02 | 池记账不重复、不漏计；monitor 崩溃、超时、取消与后代存活不释放未知占用 |
| VC-D01 | 修改后旧测试结果过期；大 diff 有界；提交前文件变化拒绝陈旧选择 |
| VC-C01 | CI 结果只匹配目标 SHA；超时/无权限/缺少 workflow 显示真实状态 |
| VC-O01 | 两会话的 cwd、文件、消息、取消、权限和会话记录无串扰 |
| VC-O02 | 宿主原生崩溃后各会话都有可核对记录，不自动重放；内存收益有可复现实验 |

所有原生与故障测试使用隔离目录和受控夹具；不以用户正在运行的任务作为破坏性测试对象。执行后在 IMPLEMENTATION 记录成功、失败、受阻和原始证据。

## 10. 默认决策与暂缓项

默认采用“先队列，再共享池，再 Omp 宿主”的顺序；用户不需要先决定线程、IPC 或 Job 参数。任务卡以手工创建/导入为起点，不默认调用额外模型拆任务。

暂缓：跨机器调度、自动合并、自动广播聊天上下文、自动恢复最后一条有副作用的命令、插件市场、嵌入式终端、为所有 MCP 强行复用进程。以后需要时分别立项，不借本轮规划隐式扩大实施范围。
