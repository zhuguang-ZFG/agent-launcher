## 2. 已经存在、且不等于本文目标的行为

下列行为已经写在 `b3ba333` 的代码或 §83–§84，本文把它们当作现状，不把它们重新标成通过，也不把它们说成三台已收敛。

- 一次远程启动最多一条同步会话。`WorkspaceSync` 按主机的 `None`、`Mutagen` 或 `SshfsMount` 选择。没有「本机同时作为京云与阿里云两条会话的枢纽」这一聚合。
- Mutagen 创建参数包含 `--sync-mode two-way-resolved`，本地路径在前，远程路径在后。按第 9 节打开的 Mutagen 文档，`two-way-resolved` 让 alpha 赢得全部分歧，包括 alpha 的删除覆盖 beta 的修改或新建，并且不会留下冲突。当前代码注释写「冲突时保留两个版本」。该注释与上述文档不一致。在同权会话改成 `two-way-safe` 之前，现有会话不能用来证明双方修改已被保留。
- 就绪判据是 2 分钟内出现 `Status: Watching for changes` 且没有 `Transition problems:`。只看到 Watching 时继续等待。这是单条会话的启动门槛。
- 结束时先 `mutagen sync flush`。失败或超时则保留会话，并把错误写入回执；成功才 terminate。`attempts/<id>/sync-final.json` 用 `synced` 或 `problem` 记下这一次结束。
- `attempts/<id>/sync-session.json` 保存会话名、本地路径、远程路径和写入时间。配置窗口重启后，徽章用这个名字匹配 `mutagen sync list`。这是单条会话的名字恢复，不是冲突清单，也不是三台收敛证明。
- 现有徽章状态是未同步、同步中、就绪、有问题、已同步、同步有问题。自动刷新约 15 秒一次，单次 `mutagen sync list` 超时 10 秒。探针失败时现有界面把该槽标成未同步。本文的「未知」还没实现；在实现之前，这个「未同步」只表示现有徽章，不能当成第 4 节的当前状态。
- 「已同步」只表示该次尝试结束时 flush 成功。它是终态回退，不是两条链路此刻都已收敛。
- SSHFS 现有徽章使用「同步中」，说明文件经挂载点读写。那是挂载提示。本文不把它定义为已收敛。
- `None` 可以保存和启动。这次启动不是同权。当前实现不拒绝 `None`。
- §83–§84 的双 VPS 记录是当时各一条本机到单台云的路径。那些路径与结论保持原样。它们不是本机、京云、阿里云同时在线的三机通过。

## 3. 三机拓扑与一致性边界

同权的三台机器仍是操作者的本机 Windows、京云和阿里云。文档不写真实主机名、地址、用户名或密钥。京云与阿里云上的 agent 仍在各自的远端机器上运行。远端进程没有本机文件系统的直接访问权。

同权目标下的通常拓扑是两条 Mutagen 会话，本机是枢纽：

| 会话 | alpha | beta |
| --- | --- | --- |
| 本机—京云 | 本机上的同一项目目录 | 京云上的对应项目目录 |
| 本机—阿里云 | 本机上的同一项目目录 | 阿里云上的对应项目目录 |

alpha 放在本机，只是为了和现有创建顺序一致。同权会话使用 `two-way-safe` 时，alpha 并不自动赢得双方修改。本文不创建京云与阿里云之间的第三条会话。Mutagen 文档允许两个端点都在远端、由本机代理；那不是本产品的通常拓扑，本文也不把它说成已经启用。

因此：

- 京云上的修改先进入本机会话，再由本机—阿里云会话传到阿里云。方向相反时同样经过本机。这是两段独立周期，不是三台磁盘上的一次原子提交。
- 每条链路显示两端角色和当前状态。只有本次 list 能确认仅有一端仍有未传播修改时，才附加「京云→本机」这样的方向。两端都有修改，或无法判断时，只显示两端角色，不编造方向，也不显示 URL。
- 整体「全部已收敛」只在第 4 节的两条必要链路同时满足时出现，并且必须带着可核对的观测时间。SSH 进程仍在、退出码不是 255、或者重新挂接已经打开新的本地 SSH，都不构成同步成功。
- 本机这个枢纽离线时，两条会话都不再推进。京云在这段时间里的修改留在京云，阿里云看不到；阿里云上的修改同样到不了京云。恢复后继续使用原来的会话和它已有的历史，不先 terminate 再重建。链路恢复并保持可收敛之后，只有一侧改过的文件才进入第 8 节的 120 秒观察；到时仍未出现则该次验收失败，观察窗不是到达保证。两侧改了同一路径则进入冲突清单。恢复本身不保证立刻一致。
- 只有一台云参加这次共享目录时，没有三机整体状态。那一条链路至多显示「单链路已收敛」。

Mutagen 的周期是扫描、调和、暂存和应用。文档里的 “almost instantly” 是来源对常见小改动的描述，不是本产品的时限。本产品只对第 8 节里的小型验收文件给出 120 秒观察窗。

## 4. 状态、优先级和观测时间

每条链路的当前状态只用这一次新鲜观测计算。上次成功观测的时间始终单独显示，例如「上次观测 14:02:11」。观测过期以后，上次的标签仍可称作上次观测，不能升为当前已收敛。

| 当前状态 | 何时使用 |
| --- | --- |
| 安全暂停 | Mutagen 因一端的同步根被删除、只有一端把同步根清空，或同步根被换成另一种类型而停住会话，或操作员显式 pause。详情写明是哪一种。原因无法归类时仍用安全暂停。 |
| 冲突 | 新鲜的 `mutagen sync list` 为该会话列出至少一个可解析冲突。 |
| 未知 | 探针失败，或上次成功观测距离现在超过 30 秒。探针失败包括找不到命令、超时、非零退出和输出为空。冲突段完全无法解析、并且没有任何安全冲突行时，也是未知。已经有安全冲突行时按第 5 节保持冲突。 |
| 离线 | 这次 list 成功，并且该远端端点被识别为连接失败。不能确认是连接失败时不用离线。会话内容能解析、但达不到已收敛时用未收敛；输出无法解析时用未知。 |
| 未收敛 | 会话还在，但还不能叫已收敛。转换问题、`two-way-resolved`、以及无法确认为同步中的非 Watching 状态，都归这里。 |
| 同步中 | 能确认这一轮正在扫描、暂存或应用，同时没有安全暂停、冲突、转换问题或离线。确认不了时用未收敛。 |
| 已收敛 | 会话是 `two-way-safe`，状态为 Watching，没有 Transition problems，没有冲突，没有 pause，没有安全 halt，并且成功观测在 30 秒以内。这个标签表示该次观测没有未处理问题。它不代替 R35 的字节比较，也不表示观测之后的新写入已经到达。 |

`two-way-resolved` 会话不能进入已收敛。它的当前状态最高是未收敛，详情说明该模式会让 alpha 赢得冲突。按现有创建参数，alpha 是本机路径。

整体标签按下面的顺序取第一条已经成立的条件。详情仍逐条写出每条链路的状态和上次观测时间，整体标签不抹掉另一条：

1. 任一必要链路是安全暂停，整体为安全暂停。
2. 任一必要链路有未处理冲突，整体为冲突。
3. 任一必要链路当前为未知，整体为未知。
4. 任一必要链路离线，整体为离线。
5. 任一必要链路未收敛，整体为未收敛。
6. 任一必要链路同步中，且更高项都不成立，整体为同步中。
7. 两条必要链路都是已收敛，整体才是全部已收敛。

诊断默认只读。自动 `mutagen sync list` 同时只跑一个，间隔不短于现有的 15 秒，单次超时沿用 10 秒；窗口关闭或不再显示该徽章时停止。手动重试每次点击只发一次，超时同样 10 秒，没有后续自动循环。诊断不调用 flush，不调用 reset，不新建 SSH，也不新增自动重连计时器。

30 秒这个过期线取自现有 15 秒节流再加上一次 10 秒超时后的余量。它只决定「能不能把上次结果当成当前状态」。它不是传播时限。传播观察窗是 120 秒，与现有就绪等待同长，并且只覆盖第 8 节的小型文件。

界面在展示 Mutagen 或 SSH 的错误文本前，去掉地址、用户名、密钥路径和文件正文。可以保留已有的 `agent-launcher-` 会话名，以及槽位上本来就显示的主机卡片名称。冲突清单不附加 Address、端口或 URL。

## 5. 冲突清单与显式处理

双方修改同一相对路径，或双方新建出不同内容时，同权会话必须把该路径留在清单里。实现不得静默覆盖，不得把 `two-way-resolved` 设成同权默认，不得自动合并，也不得自动选一侧。

`two-way-safe` 仍会自动处理 Mutagen 文档所称「不会丢失未同步数据」的情形，例如一侧的修改可以覆盖另一侧的删除。那是来源的模式行为。本文不把这种自动处理扩成「双方修改也选一边」。

清单默认只读，每一行包含：

- 相对路径。空路径、绝对路径、盘符、UNC、以及任何含 `..` 段的路径都丢弃，并且不显示。该会话只要还剩至少一个安全的冲突行，当前状态就是冲突，详情注明还有无法展示的条目。一条安全冲突都没有、同时又有无法展示的条目时，当前状态是未知。
- 受影响会话，使用「本机—京云」或「本机—阿里云」。
- 分歧的两端角色。不显示文件内容、哈希或 URL。

最多显示 50 行，并写出未显示的剩余条数。超过 50 行时整体仍是冲突，不能因为被截断就显示全部已收敛。

处理动作不是默认按钮，而且只对清单中的单个文件可用。目录冲突只展示，不提供删除按钮。操作员先选中一个文件行，再选择要丢弃的一端，然后二次确认。确认文案写明相对路径和被丢弃的一端。确认后只删除那一端上的该文件；这是第 9 节里 Mutagen 与 Coder Desktop 都写明的消解方式：删掉应失败的一端，删除可以被另一端覆盖。没有「全部采用某一侧」。删除完成后只再 list 一次。冲突还在就保留该行。本轮不实现这个按钮。

未处理完的冲突存在时，整体标签不能是全部已收敛。未知和探针失败同样不能写成成功。

## 6. None 与 SSHFS

`None` 继续允许保存和启动。界面保持「这次不是同权」，当前状态不是已收敛，也不是全部已收敛。本文不把「拒绝 None」写成目标。

SSHFS 继续是已经允许的单机挂载备选，依赖现有的 WinFsp 与 SSHFS-Win。目标文案是挂载成功为「已挂载」，失败为「挂载失败」。这两种都不是已收敛，更不是三台总线。SSHFS 不把京云的修改传到阿里云。现有挂载参数里的 reconnect 是 sshfs 自己的挂载选项；本文不新增，也不把它解释成 Agent SSH 的自动重连或同步成功。

## 7. 会话生命周期

下表是实现落地后的目标，不是 `b3ba333` 的当前行为。当前创建参数仍是第 2 节的 `two-way-resolved`。

Mutagen 用会话里已达成的内容做三方比较，从而认出每一端的修改和冲突。terminate 后再 create，或者 `mutagen sync reset`，都会丢掉这份历史。普通故障路径因此不重建会话。暂停和恢复各是一次显式操作，本轮不实现；它们与冲突处理、确认释放、重新挂接分开。

| 事件 | 会话 | 历史与界面 |
| --- | --- | --- |
| 为同权新建会话 | `create`，模式 `two-way-safe`，名字写入该尝试的 `sync-session.json` | 只对新建会话使用新历史。不批量 terminate 已有会话来改模式。 |
| 普通离线、单条链路断开、探针失败 | 不 terminate，不 create | 名字和历史保留。当前状态按第 4 节显示。 |
| 操作员暂停 | `pause` 同一会话 | 历史保留。当前状态为安全暂停，详情写操作员暂停。 |
| 操作员恢复 | `resume` 同一会话 | 沿用原历史。恢复后重新 list，不直接显示已收敛。 |
| Mutagen 安全暂停 | 保持 halted。触发条件是一端的同步根被删除、只有一端把同步根清空，或一端的同步根换成了另一种类型 | 历史保留。不自动 resume，不自动 reset。 |
| 尝试结束且 flush 成功 | 保持现有顺序：flush 成功后 terminate | 这是现有结束行为。`sync-final.json` 仍可记 `synced`。该记录显示为结束时结果，不改写成三台当前已收敛。 |
| 尝试结束且 flush 失败或超时 | 保持现有规则：不 terminate，回执记录错误 | `sync-final.json` 记 `problem`。界面用现有的「同步有问题」，不用已收敛。 |
| 操作员确认释放 | 不把释放定义成同步成功，不删除 `sync-session.json` 来假装历史已清理 | 释放协议仍以 C14 与 R28 为准。本文不新写 `operator-release.json`。若结束路径同时 flush，失败时仍保留会话。 |
| 破坏性重置 | `reset`，或 terminate 后再 create | 会丢掉三方合并历史。必须用单独的确认，确认文案与冲突处理、释放、重新挂接都分开。未确认不执行。本轮只写这条，不执行。 |

同权新建会话使用 `two-way-safe` 只约束实现落地之后创建的会话。已经存在的 `two-way-resolved` 会话留在原地，并按第 4 节禁止进入已收敛。操作员若要替换其中某一个，走破坏性重置的单独确认。

重新挂接的按钮、协议和拒绝条件以第 1 节的依赖为准。普通离线不调用那条路径，也不会为了同步而自动打开 SSH。

## 8. 验收

状态词汇仍只有未执行、通过、失败、受阻。本表现在每一行都是未执行。规格写入不改变这个状态。fake 用夹具或假的 list 输出，不打开真实 VPS。R44 才是三台活测，而且现在没有执行。

观察窗只适用于验收夹具：每个新文件不超过 4 KiB，相对路径不落在现有忽略规则内。现有创建参数忽略 `.git`、`node_modules/`、`bin/` 和 `obj/`。本文不扩大忽略列表，也不给任意大目录规定 120 秒。120 秒到了仍不一致时，结果是未收敛或冲突，测试失败，不能把阈值放宽后算通过。

## 9. 来源

2026-11-18 重新打开并核对了下面四处。来源能做到的事，只说明 Mutagen 或 Coder Desktop 的能力。它不证明本软件已经做到，也不证明 R34～R44 已执行。

- [Mutagen 文件同步](https://mutagen.io/documentation/synchronization)。会话有 alpha 与 beta。两端都可以在远端，那时本机只做代理；本文的通常拓扑不使用这种京云—阿里云直连会话。模式有 `two-way-safe`（默认）、`two-way-resolved`、`one-way-safe`、`one-way-replica`。`two-way-safe` 只自动处理不会丢失未同步数据的分歧，不能自动处理的冲突留在会话里，可用 `mutagen sync list` 列出；消解方式是删掉应失败的一端。`two-way-resolved` 由 alpha 赢得全部冲突，包括 alpha 的删除覆盖 beta 的修改或新建，并且不会产生冲突。管理命令包括 `create`、`list`、`monitor`、`flush`、`pause`、`resume`、`terminate`。
- [Mutagen 安全机制](https://mutagen.io/documentation/synchronization/safety-mechanisms)。一端的同步根被整棵删除、只有一端把同步根清空、以及同步根被换成另一种类型，会尽力停止会话。检测不是原子的；根被删的过程中，Mutagen 仍可能先传播其中一部分。恢复可以是手动处理后 `resume`。`reset` 会重设历史，使未删除的内容看起来像新内容。安全机制不负责方向和冲突模式。
- [mutagen-io/mutagen](https://github.com/mutagen-io/mutagen)。README 说明它在 Windows、macOS 和 Linux 上构建，并提供文件同步与网络转发，传输可以是本机、SSH 或 Docker。1.0 之前的次版本支持窗口很短。本文不锁定版本号；实现落地时另记实际使用的版本。网络转发不在本文范围。
- [Coder Desktop Connect and Sync](https://coder.com/docs/user-guides/desktop/desktop-connect-sync/)。Coder 的文件同步是本地目录与工作区之间的双向同步，alpha 为本机，beta 为远端，冲突状态可以列出文件，消解方式同样是删掉不想保留的一端，并排除版本控制目录。页面里的 Connect、自动端口转发和 `.coder` 主机名属于 Coder Connect。本文不引入这些能力。Coder 写到可以离线工作，这不是本产品对离线修改一定自动合并的承诺。
